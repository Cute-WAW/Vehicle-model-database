# 远端服务器一键更新脚本说明

> 记录日期：2026-04-21
> 对应脚本：`scripts/update_all_servers.py`

## 1. 文档目的

本文档用于说明当前项目中：

- 如何使用 `update_all_servers.py` 一键同步本地改动到远端服务器
- 脚本当前具备哪些增强逻辑
- 在什么情况下脚本会自动走兜底恢复路径
- 执行后应如何判断更新是否成功

## 2. 适用服务器

当前脚本内置了两个远端服务器：

1. 腾讯云
2. 阿里云

脚本会依次连接并执行更新。

## 3. 当前脚本已增强的能力

相比原始版本，当前 `update_all_servers.py` 已新增或增强以下逻辑：

### 3.1 同步范围更完整

当前同步内容不仅包含 `src/`，还包含这轮改造中真正会影响运行结果的关键目录：

- `config/`
- `wechat/`
- `doc/`
- `experiment/`
- `tests/`
- `output/lightgbm/`
- `output/segmented_models/`
- `output/brand_series_models/`
- `output/car_types_models/`
- `price_model/`

这解决了旧脚本“代码同步了，但配置和模型没同步”的问题。

### 3.2 远端命令统一封装

脚本现在使用统一的命令执行与结果记录方式：

- 每一步命令都会记录 `exit_code`
- 同时保留 `stdout` / `stderr`
- 最终输出完整 JSON 摘要，方便排查失败点

### 3.3 重启流程分为两级

#### 正常路径

优先尝试：

```bash
compose up -d --build --force-recreate
```

适用于：

- 远端能够正常访问镜像源
- 需要基于最新 Dockerfile/requirements 重建镜像

#### 兜底路径

如果构建失败，自动退化为：

```bash
compose up -d --force-recreate --no-build
```

然后继续执行运行态补丁恢复。

### 3.4 运行态补丁恢复

当远端构建失败，但旧镜像还可用时，脚本会自动尝试：

1. 把最新 `config/` 拷贝进容器
2. 在容器内执行：

```bash
pip install -r /app/requirements.txt
```

3. 重启 Web 容器与配套容器

这个逻辑主要用于处理类似下面的情况：

- Docker Hub 超时
- 基础镜像拉取失败
- 但现有镜像仍能启动服务

### 3.5 自动健康检查

更新完成后，脚本会自动检查远端健康接口。

当前约定：

- 腾讯云检查：`http://127.0.0.1:8087/health`
- 阿里云检查：`http://127.0.0.1:8096/health`

只有健康检查通过，才算当前服务器更新成功。

### 3.6 自动输出最终摘要

脚本结束后会输出一份 JSON 摘要，包含：

- 服务器名称
- 远端项目目录
- 执行模式
  - `build`
  - `fallback_no_build`
- 最终状态
- 健康检查结果
- 每一步执行日志

## 4. 当前使用方法

在项目根目录执行：

```powershell
..\venv\Scripts\python.exe scripts\update_all_servers.py
```

## 5. 脚本实际执行步骤

每台服务器的执行顺序如下：

1. SSH 连接远端服务器
2. 定位远端项目目录
3. 打包并上传更新压缩包
4. 在远端解压覆盖文件
5. 修复 `users.sqlite` 文件形态
6. 删除可能冲突的旧容器
7. 删除旧的索引缓存文件
8. 尝试执行 `compose up --build`
9. 若失败，则进入 `--no-build` 兜底路径
10. 若进入兜底路径，则执行运行态补丁恢复
11. 检查健康接口
12. 输出 `docker ps`

## 6. 成功判断标准

执行成功至少需要满足：

1. 脚本输出中两台服务器的 `status` 为 `ok`
2. 健康检查返回中包含：

```json
{"status":"ok","predictor_ready":true}
```

3. 远端 `docker ps` 中能看到对应 Web 容器处于 `Up` 状态

## 7. 常见失败场景与处理方式

### 7.1 Docker Hub 拉取超时

典型现象：

- `python:3.9-slim` 拉取失败
- `compose up --build` 超时

当前脚本处理方式：

- 自动退回 `--no-build`
- 再通过容器内 `pip install -r requirements.txt` 补齐依赖

### 7.2 旧容器占端口

典型现象：

- 旧容器未删除，导致新容器无法启动

当前脚本处理方式：

- 在重启前自动执行容器清理

### 7.3 配置没同步导致默认行为不一致

典型现象：

- 本地默认 `lightgbm`
- 远端仍走 `curve`

当前脚本处理方式：

- `config/` 已纳入同步范围
- 兜底路径还会把 `config/` 再复制进容器

## 8. 建议配套命令

更新完成后，可再执行：

```powershell
..\venv\Scripts\python.exe scripts\check_servers_status.py
```

用于快速查看两台服务器当前运行中的容器状态。

## 9. 当前结论

当前版本的 `update_all_servers.py` 已经从“纯上传 + 重启”增强为：

- 可同步完整改动
- 可处理构建失败场景
- 可自动恢复服务
- 可自动做健康检查

因此，后续正常更新两个远端服务器，优先建议直接使用该脚本，而不是手动逐台上传与重启。
